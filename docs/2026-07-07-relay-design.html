Relay Design Spec

Working codename Relay · 2026-07-07 · Status: design locked, pending review → writing-plans

An accessible-by-default, AI-assisted ITSM request tool — a minified ideal ServiceNow — where one plain-language box replaces the confusing intake, Claude classifies and structures the input into correctly-typed records, and a single consolidated workspace kills the REQ→RITM→SCTASK three-page navigation tax. Reskinnable across an entire employer funnel by swapping data, not code.

Why this project exists

This is flagship #1 of two (the second — a game-companion app — is a separate, later project, NOT in this spec). It proves the edge: "IT/enterprise operator who now ships, with AI as leverage." Built against a category (AI-leverage tooling for unsexy IT/ops workflows), not one company, and reskinned per application in ~30 min — resume, not cover letter. Grounded in lived pain: a daily ServiceNow user on a school-district service desk running an ITSM never configured for the team.

The pains it kills

  1. Intake confusion. Users get lost choosing a ticket type. → One plain-language box. Never pick a type.
  2. Request fragmentation. One request shattered across three pages — REQ → RITM → SCTASK. → One consolidated workspace, whole tree actionable inline.
  3. Weak search. Fuzzy search underperforms. → AI semantic deflection at intake (built last).
  4. Inaccessibility. Hostile to assistive tech. → Keyboard- and screen-reader-first, low-vision teammate as north-star. Public sector = real 508/WCAG obligations = hiring signal for the internal-tools funnel.

Users — both sides, one flow

  • Requester: describes a need/problem in plain language; AI forms the records so they never touch the catalog.
  • Fulfiller / agent: the AI-structured request lands in a decluttered consolidated workspace — full REQ/RITM/SCTASK tree on one page.

The AI capabilities (all load-bearing)

  1. Classify intent — incident vs. request — and route to the correct record type. The transferable "right front door" skill.
  2. Decompose & structure — request → REQ + correct RITMs, infer fields, ask only for genuinely-missing info. Incidents: classified + routed only, no management.
  3. Semantic deflection — surface relevant KB articles before a ticket is created. Second AI pattern; built last, the clean cut-line.

Mechanism (tool-use vs. structured output, model choice) deferred to plan phase, pinned via the claude-api skill. Claude key is server-side only.

Accessibility approach (the differentiator)

  • Built on React Aria Components — correct a11y is easy to get subtly wrong by hand; React Aria removes the footguns so it's real, not aspirational. Strongest interview answer. Fallback: base-ui (already known) if velocity stalls.
  • Keyboard-first, screen-reader-first; customizable shortcuts + high-contrast/adjustable display for the low-vision user.
  • The single-page workspace is itself an a11y win — fewer navigation stops.

Architecture

  • Framework: Next.js + TypeScript, single repo.
  • AI: Claude API from a server-side route (key never client-side).
  • UI: React Aria Components.
  • Persistence: lightweight DB — Supabase/Postgres vs. SQLite decided at plan time.
  • Deploy: Vercel.

The reskin seam — HARD REQUIREMENT

The catalog, record schema, fulfillment hierarchy, and branding all live as DATA / config, not code. The engine is domain-agnostic and never edited per application. Per application: swap catalog/schema data, swap branding, write one demo scenario from the target's G2/Capterra pain.

Data model (the slice)

  • Incident — standalone; created + routed, no management.
  • Request (REQ) → RequestItem (RITM) (1..n) → CatalogTask (SCTASK) (0..n).
  • CatalogItem + field defs — config/data, the reskin surface.
  • KB Article — small demo set for deflection.

Data flow

  1. User types plain-language input.
  2. Server route sends input + catalog schema to Claude.
  3. (Deflection, last) semantic KB search; user may self-resolve.
  4. Claude returns record type, matched items, inferred values, what's missing.
  5. Minimal clarification loop for missing required fields.
  6. Records created & persisted.
  7. Fulfiller opens the consolidated workspace.

Error handling

  • Malformed/low-confidence AI output: validate against schema server-side; fall back to a confirm path, never create garbage.
  • Missing required fields: the clarification loop is the designed path.
  • AI/API down: degrade to an accessible manual structured form.
  • Search miss: just create the ticket (deflection is additive).

"Done" = demo-ready

  • Two end-to-end scenarios: a multi-item onboarding request; an incident. Plus a live deflection example.
  • Deployed to Vercel.
  • Passes axe/Lighthouse audit + full keyboard walkthrough + screen-reader walkthrough.
  • Phase-2 list documented in-repo.

Explicitly OUT of scope (phase 2+)

  • KB authoring / approval / browse (overlaps kb-helper / knowflow — do not rebuild).
  • Approvals / SLAs, change / problem / CMDB.
  • Real ServiceNow integration.
  • AI-learned config recommender.
  • Real auth / RBAC beyond a demo toggle.
  • Performance/load-time tuning (not an AI story).

Open items for the plan phase

  • Persistence choice (Supabase/Postgres vs. SQLite).
  • Exact Claude mechanism (tool use vs. structured output) — via claude-api.
  • Semantic search at demo scale (embeddings vs. small-set in-context) — keep minimal.
  • Synthetic district catalog + small KB article set.

Decisions locked this session

  • Two flagships; build this IT/ops tool first, then the game-companion app (separate session).
  • Core = smart request intake + consolidated workspace; a11y-first; district skin.
  • Users = both requester + fulfiller, one flow.
  • Front door includes lightweight incident classification.
  • KB = semantic deflection only (built last); authoring/cleanup OUT.
  • Stack = Next.js + TS + Claude (server-side) + React Aria + Vercel.
  • Name = working codename "Relay"; rename freely.
