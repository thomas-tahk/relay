Relay Implementation Plan

2026-07-07 · Skim view — the canonical plan with full per-step code is the sibling .md. Execute via superpowers:subagent-driven-development.

Goal: Ship the Relay MVP — an accessible-by-default AI ITSM intake tool where one plain-language box classifies + structures a request or incident, and a consolidated workspace shows the whole REQ/RITM/SCTASK tree on one page.

Architecture & stack

Next.js (App Router) + TypeScript, single repo. A server-side API route calls Claude (messages.parse() with a JSON schema) to turn plain-language input + the catalog schema into a typed, validated record set. A thin RecordStore hides persistence (in-memory for tests, Supabase for the demo). React Aria Components render both screens to a high a11y bar. Catalog + branding live in config/ so the app reskins by data swap.

Stack: Next.js 15 · TypeScript · @anthropic-ai/sdk · React Aria Components · Zod · Supabase · Vitest · Playwright + axe-core · Vercel.

Global constraints

  • Model claude-opus-4-8 (verified current); Haiku/Sonnet is a cost lever — user's call only.
  • Claude key server-side only; never import the SDK into a client component.
  • Structured output via messages.parse() + zodOutputFormat — no prefills (400 on Opus 4.8), no deprecated output_format.
  • Reskin seam is load-bearing: catalog / fields / hierarchy / branding are DATA in config/; no engine module imports district strings.
  • Accessibility is a gate — final axe pass must be clean.
  • Scope: request lifecycle + lightweight incident classification. Spec's OUT list stays out.

Phases & tasks

Phase 0 — Scaffold

  • T0 create-next-app, install deps (anthropic sdk, react-aria-components, zod, supabase, vitest, playwright+axe), env placeholders, test runner green.

Phase 1 — Domain + Data (TDD)

  • T1 Domain types: Incident, Request(REQ)→RequestItem(RITM)→CatalogTask(SCTASK), CatalogItem, RecordTree.
  • T2 District catalog.ts (laptop, email, SIS access, software bundle) + Zod IntakeResultSchema (discriminated union on kind).
  • T3 RecordStore interface + in-memory impl (save tree, get, list, toggleTask).
Request  = { id, summary, createdAt, items: RequestItem[] }
RequestItem = { id, reqId, catalogItemId, values, tasks: CatalogTask[] }
CatalogTask = { id, ritmId, label, done }
Incident = { id, shortDescription, category, urgency, affectedItem, createdAt }

Phase 2 — AI intake (load-bearing, TDD)

  • T4 buildIntakeSystemPrompt(catalog) — instructs: incident vs request, match items, infer fields, list genuinely-missing required fields.
  • T5 runIntake(input, {client}) — the Claude call (mockable client for tests):
const res = await client.messages.parse({
  model: "claude-opus-4-8", max_tokens: 4096,
  thinking: { type: "adaptive" },            // tunable; drop for latency
  system: buildIntakeSystemPrompt(catalog),
  output_config: { format: zodOutputFormat(IntakeResultSchema) },
  messages: [{ role: "user", content: input }],
});
if (!res.parsed_output) throw new Error("intake_unparseable");
return res.parsed_output;
  • T6 validateAgainstCatalog() (still-missing required keys) + assembleTree() (IntakeResult → REQ+RITMs+default SCTASKs, or Incident).

Phase 3 — API routes (TDD)

  • T7 POST /api/intake → { result, missing }; empty body 400; key stays server-side.
  • T8 /api/records — POST (assemble+save), GET list, GET [id] tree.
  • T9 Supabase store + schema.sql; getStore() picks Supabase when env present, memory otherwise.

Phase 4 — Requester UI, a11y-first (e2e TDD)

  • T10 IntakeBox (React Aria TextField/Label/Button) → POST intake → structured preview. Manual-form fallback if AI fails.
  • T11 ClarifyDialog — asks ONLY the missing required fields → POST records → confirmation with REQ id.

Phase 5 — Fulfiller workspace (e2e TDD)

  • T12 /workspace queue — keyboard-focusable list of requests.
  • T13 RequestTree — REQ header → RITM cards → SCTASK checkboxes, one page (kills the 3-page tax); toggles persist.

Phase 6 — Accessibility gate + demo

  • T14 axe-core zero-violations on all screens; documented keyboard + VoiceOver walkthrough; customizable shortcuts + high-contrast/large-text toggle for the low-vision north-star user.
  • T15 Two hero scenarios end-to-end: onboarding request (multi-RITM) + projector incident.

Phase 7 — Semantic deflection (THE CUT LINE)

Build only if 0–6 are green with time to spare. Everything above ships without it.
  • T16 ~24 demo KB articles as DATA; suggestArticles(text, kb) via one Claude relevance call over the small in-context KB (no vector DB); surface suggestions at intake before ticket creation. Deflection is additive, never a gate.

Phase 8 — Deploy

  • T17 Vercel env (keys never in repo); run both scenarios + axe against the live URL; write KNOWN-ISSUES + README (incl. the reskin playbook).

Definition of done

Both hero scenarios run end-to-end on Vercel · axe/Lighthouse clean · full keyboard + screen-reader walkthrough pass · phase-2 backlog documented.

Error handling

  • Malformed/low-confidence AI → 422 → manual accessible form; never persist garbage.
  • Missing required fields → the clarification loop, not an error.
  • Claude API down → 503 → manual form; app never fully blocked by the model.
  • Deflection miss → just create the ticket.
